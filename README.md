## 这是什么

SmartMarkr 是一个浏览器书签治理扩展，解决四类高频问题：

1. **重复堆积** —— 同一页面被反复收藏，URL 只差 `?utm_source=` 或结尾斜杠
2. **死链残留** —— 早已 404 的页面仍留在书签栏里
3. **结构混乱** —— 书签平铺在根目录，找不到、也没空整理
4. **误删不可逆** —— 批量清理后想找回，却已经晚了

它把这些操作全部放在浏览器本地完成，不引入账号体系、不依赖服务器、不上传任何数据。

适用浏览器：Chrome、Edge，以及任何支持 Manifest V3 的 Chromium 内核浏览器。

## 核心能力

### 重复书签检测

两套互补的匹配策略，可单独或同时启用：

| 策略 | 原理 | 覆盖场景 |
|---|---|---|
| 精确匹配 | URL 规范化后比对 | `?utm_source=x`、`#hash`、`:443`、查询参数顺序、结尾 `/` 造成的伪重复 |
| 相似匹配 | 主域名分桶 + 标题倒排索引 + 并查集聚类 | 同一站点的重复入口，如「OpenAI 文档」与「OpenAI 官方文档」 |

URL 规范化会统一大小写主机名、移除跟踪参数（utm 系列 / fbclid / gclid / spm 等）、排序查询参数、去掉默认端口与锚点。相似匹配按可调阈值（默认 0.82）打分，综合标题 Jaccard、标题 Dice 与路径 Dice。

**性能**：5000 条书签实测约 **18ms**。候选对通过倒排索引生成而非全量两两比较，单条候选数与桶大小均有硬上限，超出会记入警告而不是卡死页面。

### 失效链接检测

- **HEAD → GET 回退**：先发 HEAD；遇到 `400 / 403 / 405 / 406 / 501` 或网络异常时，自动改用 `GET` 并携带 `Range: bytes=0-0`，避免把「不支持 HEAD 的站点」误判为失效
- **状态分类**，而不是一律当作死链：

| 状态 | HTTP | 含义 |
|---|---|---|
| 正常 | 200–299 | 可访问 |
| 重定向 | 301/302/307/308 | 可访问，跳转到新地址 |
| 失效 | 404/410 | 确认不可用，建议清理 |
| 受限 | 401/403/429 | **不是失效**，可能需要登录或触发限流 |
| 服务端错误 | 5xx | 对方服务器问题，带抖动重试 |
| 超时 | — | 超过设定时限 |

- **可控压力**：并发上限 16（默认 6），每主机独立限速（默认 300ms 一次），结果进 LRU 缓存，重复 URL 只探测一次并把结果回填给所有相同链接的书签
- **可暂停 / 可继续**：长扫描过程中随时暂停，进度保留

### 智能归档

三种归档策略：按域名、按类型、按用户自定义文件夹。支持关键词筛选、按组选择目标文件夹、批量执行；执行前自动落快照。

### 文件夹清理

识别空文件夹与重复文件夹，选中后可批量移入回收站，同样支持撤销与快照还原。

### 安全回收与快照备份

这是 2.0 相对 1.0 最大的安全改进：

- **回收站**：删除不会直接消失，先移入 `❌ 书签回收站`
- **快照**：每次批量删除或归档**之前**，自动写入一份完整书签树快照，保留最近 5 份
- **可还原**：快照面板支持一键还原、导出 JSON、导出 Netscape HTML、单条删除
- **内置根节点复用**：还原时复用浏览器自身的「书签栏 / 其他书签」根节点，不会重复创建根目录

### 导入导出

| 能力 | 说明 |
|---|---|
| 导出 | 自有 JSON 备份格式，或通用 Netscape HTML（Chrome / Edge / Firefox 均可导入） |
| 导出标签页 | 把当前所有标签页一并导出，或单独导出为书签文件夹 |
| 导入 | 解析 Netscape HTML 与自有 JSON；解析器容忍畸形标签、HTML 实体、UTF-8 BOM、未闭合 `<DL>` |
| 重复处理策略 | 「跳过已存在」（默认）/「仍然创建副本」/「覆盖同链接书签」，按规范化 URL 判定 |

## 安装

### 从源码加载（推荐，2.0 尚未上架商店）

1. 克隆或下载本仓库
2. 打开 `chrome://extensions/`（Edge 为 `edge://extensions/`）
3. 打开右上角「开发者模式」
4. 点击「加载已解压的扩展程序」，选择本仓库根目录
5. 点击工具栏中的 SmartMarkr 图标，进入管理界面

> 界面为单页应用，所有功能都在同一个标签页中，通过顶部导航切换模块。

## 使用指南

### 清理重复书签

1. 打开「重复书签」模块
2. 勾选匹配方式（精确 / 相似），必要时调整相似度阈值
3. 点击「开始检测」
4. 用「智能选择」按保留规则（最早 / 最新 / 最短 URL 等）自动勾选待删项，或手动勾选
5. 点击删除，内容进入回收站；需要时用顶部「撤销上一步」找回

### 扫描失效链接

1. 打开「异常书签」模块
2. 选择要报告的类型（空链接 / 无效 URL / 超时 / 状态码异常）
3. 设置超时时间与并发数（并发越高越快，但对目标站点压力越大）
4. 点击「开始检测」，过程中可暂停
5. 按结果清理，注意「受限」类不是失效

### 备份与还原

1. 打开「快照备份」模块
2. 点击「立即创建快照」可手动备份当前书签树
3. 批量删除或归档前，系统会自动创建快照
4. 需要回退时，在列表中找到对应快照，点击「还原」
5. 也可把快照导出为 JSON / HTML 保存到别处

## 架构

```text
SmartMarkr-PRO/
├── manifest.json               Manifest V3 清单
├── background/
│   └── service-worker.js       工具栏图标入口（chrome.action）
├── manager.html                管理界面（单页）
├── styles/
│   └── manager.css             界面样式
├── scripts/
│   ├── core-utils.js           URL 规范化、主域名解析、中英分词、并发池、限速器、LRU
│   ├── dedupe.js               重复与相似书签检测引擎
│   ├── link-checker.js         链接健康检查引擎
│   ├── portable-io.js          JSON / Netscape HTML 导入导出引擎
│   ├── backup-manager.js       快照创建、列出、还原、导出
│   └── manager.js              界面控制器与 Chrome Bookmarks API 集成
├── tests/
│   ├── selftest.js             Node 20 回归测试（node:test）
│   └── e2e-mock.py             Playwright + chrome.* 桩的端到端验证
└── docs/
    └── COMPARISON.md           同类项目能力对比与取舍
```

### 依赖方向

```text
manager.js  ──uses──▶  dedupe.js
            ──uses──▶  link-checker.js
            ──uses──▶  portable-io.js
            ──uses──▶  backup-manager.js
                            │
                            ▼
                        core-utils.js   （无外部依赖）
```

四个引擎模块均为 UMD 形式：浏览器中挂载到 `globalThis.SM*`，Node 中可 `require`，因此都能脱离扩展环境做单元测试。全部为原生 JavaScript，**没有任何运行时第三方依赖**。

## 设计原则

| 原则 | 具体体现 |
|---|---|
| **本地优先** | 除用户主动触发的链接探测外不产生任何外部请求；无账号、无遥测、无云依赖 |
| **可回滚** | 批量破坏性操作先落快照，删除先进回收站，单步操作可撤销 |
| **有界资源** | 并发、缓存、候选对、分组大小、快照数量全部设上限，避免大书签库下卡顿或内存膨胀 |
| **稳健解析** | 导入解析容忍畸形 HTML、实体、BOM、未闭合标签，单条失败不影响整批 |
| **不误伤** | 区分「失效」与「受限」；覆盖式导入前强制快照 |

| 权限 | 用途 |

## 常见问题

**Q：扫描失效链接会不会把需要登录的页面当成死链？**
不会。401、403、429 被归类为「受限」而非「失效」，默认不会出现在建议删除的集合里。

**Q：相似检测会不会把不同站点但标题相近的书签误判为重复？**
候选对只在同一主域名内生成，跨域名不会被聚为一组。

**Q：清理完后悔了怎么办？**
先看「撤销上一步」；若已跨批次，进入「快照备份」还原批量操作前的快照。

**Q：书签很多，会不会卡死？**
候选对、并发、缓存、分组大小都有硬上限；5000 条去重在 JS 引擎中约 18ms。超出上限的分组会记入警告并跳过，不会阻塞界面。

**Q：数据会上传吗？**
不会。除主动探测链接可访问性外没有任何网络请求，也没有任何账号或服务端。

**Q：支持 Firefox 吗？**
清单中保留了 `browser_specific_settings`，但当前版本以 Chromium 内核为主进行验证。

## 同类项目与选型

2.0 在设计前调研了 karakeep、linkwarden、shiori、linkding、buku、floccus、sidebery 等项目的公开实现，并对能力逐项取舍。对照表与「为什么不做某方向」的说明见 [docs/COMPARISON.md](docs/COMPARISON.md)。

简要结论：

- **借鉴** URL 规范化优先、区分失效与受限、批量操作可回退、导入解析容忍现实数据、资源使用有上限
- **不采用** 自托管服务端、账号体系、云端全文检索、需要外发数据的 AI 打标签 —— 与本扩展「纯本地、零上传」的定位冲突
